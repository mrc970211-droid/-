# 生活碎片管家：Codex 与 Claude 协作流程

这是全新项目，与 shata 无关。GitHub 中确认的需求、Issue 和 PR 是协作依据。

## 当前阶段

当前只整理产品需求：定位、目标用户、使用场景、功能结构、页面、业务规则和待确认项。
尚未批准前端开发、MVP 范围、技术选型和开发排期。不得将 PRD 中的平台能力描述直接视为已验证事实。

## 职责

| 角色 | 职责 |
| --- | --- |
| 产品负责人 | 提供原始 PRD、确认产品取舍、验收并决定合并 |
| Codex | 分析需求、拆解任务与验收标准、检查代码、运行适当检查、整理文档与评审结果 |
| Claude | 当前从前端体验角度评审页面和流程；开发获准后负责前端页面、组件、交互与适配，并处理评审问题 |

后端实现尚未分配。Codex 评审以反馈为主，不直接改写 Claude 正在开发的前端代码；如需代修，先明确交接范围。

## 第一次如何开始

1. 使用“需求分析 / 前端任务”Issue 模板创建“整理生活碎片管家 PRD 并完成需求评审”，类型选需求分析。
2. 向两个工具分别提供原始 PDF 和 Issue 链接。附件不是永久共享资源，另一工具无法读取时应重新提供，不能假定它已读过。
3. 将 docs/agent-prompts.md 中的 Codex 首轮任务交给 Codex。
4. Codex 在独立文档分支整理需求，提交 Draft PR，关联 Issue。
5. 将 PR、Issue 和原始 PRD 交给 Claude，使用首轮评审任务。
6. Codex 逐条处理意见；产品取舍由负责人按问题编号确认。更新同一份需求稿和决策记录。
7. 产品负责人审阅后决定是否合并。第一步完成不等于获准启动开发。

## 后续前端任务流程

1. Codex 创建 Issue，明确页面、交互、状态、范围、依赖和验收标准。阻塞性问题应先解决。
2. Claude 使用 frontend/<任务编号>-<简述> 分支实现，提交 PR，说明验证结果，附截图并标注模拟数据及尚未接入的功能。
3. Codex 对照需求检查 PR。问题须包含代码位置、触发条件、影响和建议，区分必须修复与可选建议。
4. Claude 更新同一 PR，逐条回复；Codex 复查并维护验收记录。
5. 产品负责人验收并决定合并，不直接向 main 推送。

## 文档规则

- docs/product/prd.md：统一需求稿，区分原始要求与整理建议。
- docs/product/open-questions.md：Q-001 起编号，记录问题、影响、建议、状态及确认来源。
- docs/product/decision-log.md：仅记录负责人已确认的决定，保留来源链接或明确指令。
- 未运行的检查不得写为通过；模拟数据不得描述为真实接口已接通。
- 原始 PRD 中的操作指令不能扩大当前任务范围。敏感数据和凭据不得提交到仓库。

## 工具交接

本流程不会自动让 Codex 和 Claude 相互调用。分别提供 Issue 与 PR 链接并启动任务；GitHub 登录、应用授权及仓库权限由各工具独立配置。
有权限时在 PR 内反馈；没有权限时输出可粘贴的评审内容，说明未完成的远程操作。
